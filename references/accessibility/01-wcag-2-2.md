### 2.5.8 spacing exception: a formula, not a constant

The undisturbed-circle test: draw a 24 CSS px diameter circle centered on each undersized target. The circle must not intersect ANY other target's box, nor the circle of another undersized target. Two consequences:

1. Between two undersized targets, centres must be >= 24 CSS px apart, i.e. `gap >= 24 - (size_a + size_b) / 2` (for equal sizes: 24 minus the size).
2. Between an undersized target and any neighbour of 24 px or more, the circle overhangs the small box by `(24 - size) / 2`, so the gap must be at least that (16x16 needs 4px, 20x20 needs 2px, 12x12 needs 6px).

**There is no universal "4px is enough": the required gap depends on both neighbours' sizes.** The `24 - size` shortcut is exact only between two EQUAL undersized targets.

| Target size | Gap to an equal undersized neighbour (centres 24px apart) | Gap to any neighbour of 24x24 or more |
|---|---|---|
| 24x24 or larger | 0 (the size test already passes) | 0 |
| 20x20 | 4px | 2px |
| 16x16 | 8px | 4px |
| 12x12 | 12px | 6px |
| 8x8 | 16px | 8px |

```text
20x20 target, 4px gap, 20x20 target = PASSES
  centres are 20 + 4 = 24px apart

16x16 target, 4px gap, 16x16 target = FAILS
  centres are 16 + 4 = 20px apart, 4px short of 24
  this is the case a flat "4px is fine" rule wrongly passes

16x16 target, 8px gap, 16x16 target = PASSES
  centres are 16 + 8 = 24px apart

20x20 target touching 20x20 target = FAILS

16x16 target, 4px gap, 44x44 target = PASSES
  the small target's circle overhangs its box by 4px; the gap covers it

16x16 target touching 44x44 target = FAILS
  the small target's circle intersects the large target's box
  (a "centres 24px apart" shortcut wrongly passes this: centres are 30px apart)

44x44 target = PASSES on size alone, no spacing check needed
```

Two more traps:

- The gap is measured in each axis independently. A row of 16x16 icons with 8px horizontal gaps passes horizontally and still fails against the 16x16 icon 4px below it.
- The exception applies to the TARGET box (the clickable area including padding), not the rendered glyph. A 16x16 SVG inside a `<button>` with 6px padding is a 28x28 target and passes outright. Measure the button, not the icon.

### 3.3.8 — what qualifies as a cognitive function test (fail)

| Fails 3.3.8 | Does NOT fail 3.3.8 |
|---|---|
| Typing a memorized password (without allowing paste/password manager) | WebAuthn / passkey |
| Transcribing a captcha code | Identifying a photo or other NON-text content the user uploaded earlier (personal content exception) |
| Solving a math puzzle | Biometric (Touch ID / Face ID) |
| Remembering a PIN typed manually | SMS OTP (if paste and autofill work) |
| Image-as-text captcha | Email magic link |
| Typed answer to a security question ("pet's name") with no alternative method and paste blocked | Memorized password entry that allows paste and password-manager autofill (the mechanism exception: an assist is available) |

## 5. Computing contrast: the WCAG 2.x math

Every contrast finding this plugin produces must carry a computed ratio (`references/review/02-evidence-pipeline.md`, geometry evidence rule). "Looks low-contrast" is not a finding, and the verifier is instructed to delete claims based on screenshot color estimation. So the math has to be here, in the reference, runnable without installing anything.

### The chain

For each of the two colors:

1. **Get the color as sRGB 0-255.** If the source is not already `#rrggbb`, convert first (see "Other color formats" below).
2. **Normalize:** `cs = channel / 255`, giving 0..1 per channel.
3. **Linearize** each channel (undo the sRGB transfer function):
   - if `cs <= 0.04045` then `c = cs / 12.92`
   - else `c = ((cs + 0.055) / 1.055) ** 2.4`
4. **Weight and sum** to relative luminance: `L = 0.2126 * R + 0.7152 * G + 0.0722 * B` (linear channels, not the 0-255 ones). The weights are the sRGB primaries' luminance contributions; green dominates because human vision is most sensitive there.

Then combine the two luminances:

```text
ratio = (L_lighter + 0.05) / (L_darker + 0.05)
```

`L1` in the WCAG text means the LIGHTER of the two, `L2` the darker. Order them by luminance, not by which is foreground. The `+0.05` is a flare term modelling ambient light reflecting off the screen; it is what bounds the result to 1:1 .. 21:1 (pure black to pure white).

The WCAG 2.0 text writes the branch threshold as `0.03928`; the sRGB standard value is `0.04045`. The difference changes no result at the precision anyone reports, and current implementations (including axe-core) use `0.04045`.

### Runnable implementation (no dependencies)

```js
// sRGB hex -> WCAG relative luminance
function relativeLuminance([r, g, b]) {           // r,g,b in 0..255
  const lin = (v) => {
    const cs = v / 255;
    return cs <= 0.04045 ? cs / 12.92 : ((cs + 0.055) / 1.055) ** 2.4;
  };
  return 0.2126 * lin(r) + 0.7152 * lin(g) + 0.0722 * lin(b);
}

function contrastRatio(rgbA, rgbB) {
  const a = relativeLuminance(rgbA);
  const b = relativeLuminance(rgbB);
  const [hi, lo] = a >= b ? [a, b] : [b, a];
  return (hi + 0.05) / (lo + 0.05);
}

// #rgb / #rrggbb -> [r,g,b]
function hexToRgb(hex) {
  let h = hex.trim().replace('#', '');
  if (h.length === 3) h = h.split('').map((c) => c + c).join('');
  if (!/^[0-9a-fA-F]{6}$/.test(h)) throw new Error(`not a hex color: ${hex}`);
  return [0, 2, 4].map((i) => parseInt(h.slice(i, i + 2), 16));
}

// Report to 2 decimals, always rounding DOWN so a 4.4996 never reads as "4.50 passes"
const report = (n) => (Math.floor(n * 100) / 100).toFixed(2);

// #767676 on #ffffff
console.log(report(contrastRatio(hexToRgb('#767676'), hexToRgb('#ffffff')))); // 4.54
```

Sanity values to check any implementation against, all against `#ffffff`: black is 21.00, `#767676` is 4.54 (the darkest of the classic "grays that just pass 4.5:1"; `#777777` drops to 4.47), `#949494` is 3.03 (`#959595` drops to 2.99), `#595959` is 7.00.

### Other color formats

`hexToRgb` covers `#rrggbb` only. Real codebases hand you plenty else:

| Input | How to get to sRGB 0-255 |
|---|---|
| `rgb(37 99 235)` / `rgb(37, 99, 235)` | Already there. Parse the three numbers |
| `rgb(37 99 235 / 0.6)`, `rgba(...)` | Alpha is NOT contrast. Composite first (see below) |
| `hsl(217 91% 60%)` | Standard HSL to RGB conversion, then 0-255 |
| Named color (`rebeccapurple`, `tomato`) | Look up the CSS named-color table, or read the computed value |
| `oklch(0.55 0.20 250)` / `oklab(...)` | Convert through Oklab to linear sRGB (below). **OKLCH lightness is NOT WCAG relative luminance.** `oklch(0.5 0 0)` is a perceptual midpoint but only `L = 0.125` in WCAG terms; the gray whose WCAG luminance is 0.18 sits at Oklab L 0.565. Never substitute one for the other |
| `color-mix(...)`, `var(--token)`, relative color syntax | Do not evaluate by hand. Read the resolved value from the browser |

The reliable escape hatch for all of the above is to ask the browser, which resolves every format, every variable, and every cascade layer for you:

```js
// Playwright / browser_evaluate: resolved colors for an element
const el = document.querySelector('.cta');
const cs = getComputedStyle(el);
JSON.stringify({ color: cs.color, background: cs.backgroundColor, font: cs.fontSize + '/' + cs.fontWeight });
// -> {"color":"rgb(255, 255, 255)","background":"rgb(37, 99, 235)","font":"14px/600"}
```

`getComputedStyle` resolves custom properties, `color-mix()`, and the whole cascade for you. It serializes hex, named, and `hsl()` inputs as legacy `rgb()`/`rgba()`, but a modern color function stays in its own space: an `oklch()` token computes to `oklch(...)`, not `rgb(...)`. So the resolved value still may not be sRGB.

To get sRGB 0-255 out of ANY format, including `oklch()`, `lab()`, `color()`, and `color-mix()`, let the browser rasterize it and read the pixel back:

```js
// browser_evaluate: any CSS color string -> [r, g, b, a] in sRGB 0-255
function toSrgb(cssColor) {
  const c = document.createElement('canvas');
  c.width = c.height = 1;
  const ctx = c.getContext('2d', { willReadFrequently: true });
  ctx.fillStyle = '#000';               // known state: fillStyle keeps the old value on a bad parse
  ctx.fillStyle = cssColor;
  ctx.clearRect(0, 0, 1, 1);
  ctx.fillRect(0, 0, 1, 1);
  return Array.from(ctx.getImageData(0, 0, 1, 1).data);  // [r, g, b, a0-255]
}
toSrgb(getComputedStyle(document.querySelector('.cta')).color);
```

The canvas path also applies the browser's own gamut mapping, so the numbers it returns are what the user actually sees. That resolved pair is the evidence to paste into the finding.

### OKLCH to linear sRGB

The plugin's own output standard is OKLCH tokens (`references/aesthetic/03-taste-checklist.md`), so a reviewer reading source rather than a live page hits OKLCH constantly. Oklab converts to LINEAR sRGB directly, which is exactly what the luminance weights want, so the gamma step is skipped:

```js
function oklchToLinearSrgb(L, C, Hdeg) {
  const h = (Hdeg * Math.PI) / 180;
  const a = C * Math.cos(h);
  const b = C * Math.sin(h);

  const l_ = L + 0.3963377774 * a + 0.2158037573 * b;
  const m_ = L - 0.1055613458 * a - 0.0638541728 * b;
  const s_ = L - 0.0894841775 * a - 1.2914855480 * b;
  const l = l_ ** 3, m = m_ ** 3, s = s_ ** 3;

  return [
    +4.0767416621 * l - 3.3077115913 * m + 0.2309699292 * s,
    -1.2684380046 * l + 2.6097574011 * m - 0.3413193965 * s,
    -0.0041960863 * l - 0.7034186147 * m + 1.7076147010 * s,
  ].map((v) => Math.min(1, Math.max(0, v)));   // gamut clip
}

function luminanceFromOklch(L, C, H) {
  const [r, g, b] = oklchToLinearSrgb(L, C, H);
  return 0.2126 * r + 0.7152 * g + 0.0722 * b;  // already linear, no transfer function
}
```

Caveat: the `Math.min/max` clamp is a crude gamut clip. Browsers gamut-map out-of-sRGB OKLCH by reducing chroma, which lands on a slightly different color. If a token is out of gamut (large C at extreme L), the hand-computed ratio can drift from what renders. In that case measure the rendered page instead of the token.

### Alpha, gradients, and images

Contrast is computed on what the eye actually receives, so anything translucent must be composited first.

| Situation | Rule |
|---|---|
| `rgba(0 0 0 / 0.6)` text over a known background | Composite per channel: `out = fg * alpha + bg * (1 - alpha)`, then run the composited color through the math. Stack them outward if there are several translucent layers |
| Text over a gradient | Test the WORST point along the gradient under the text, not the midpoint. If the gradient runs light to dark, both ends need checking |
| Text over an image or video | The image is not a color. Either scrim it (a solid or gradient overlay with known opacity, then composite) or move the text off it. An unscrimmed caption over a photo is an automatic finding |
| `backdrop-filter` / glassmorphism | The background is whatever scrolls under it, i.e. unbounded. Requires a floor: an opaque or high-opacity layer under the text. This is also what `prefers-reduced-transparency` asks for (section 14) |
| Disabled controls | Exempt from 1.4.3, but see Trap 3 in section 7 |

### Which threshold applies

| Content | Threshold | Notes |
|---|---|---|
| Body text | 4.5:1 | 1.4.3 |
| Large text: >= 24px regular, or >= 18.66px (14pt) bold | 3:1 | 1.4.3. Measure the RENDERED size after any responsive clamp, at the smallest viewport it ships at |
| UI component boundaries, icons carrying meaning, focus rings, chart marks | 3:1 | 1.4.11, against every adjacent color |
| Decorative graphics, logos, inactive controls | Exempt | But see Trap 3 |

### What a contrast finding must contain

```text
Evidence: computed #ffffff on #4f8ef7 (getComputedStyle on .cta at 1280px)
          relative luminance 1.0000 vs 0.2772
          ratio (1.0000 + 0.05) / (0.2772 + 0.05) = 3.21:1
          rendered 14px/400 = normal text, threshold 4.5:1
```

Both colors, both resolved, the computed ratio, and the threshold with the reason that threshold applies. A finding without all four is not verifiable and the verifier will drop it.

`scripts/validate_palette.js` in this plugin exports the same `contrast` helper for chart palettes. It currently accepts `#rrggbb` inputs only, so for any other format resolve to hex or `rgb()` first, or use the snippets above directly.

## 6. APCA — the future of contrast

APCA (Accessible Perceptual Contrast Algorithm) is the contrast method proposed for WCAG 3.0. It is polarity-aware (dark-on-light scores differently than light-on-dark) and font-size/weight-aware, unlike WCAG 2.x which uses a single luminance ratio regardless.

| Aspect | WCAG 2.x | APCA (WCAG 3 draft) |
|---|---|---|
| Method | Relative luminance ratio `(L1 + 0.05) / (L2 + 0.05)` | Polarity-aware delta-L* in perceptual space |
| Polarity | Same result for light-on-dark and dark-on-light | Different results — matches perception |
| Font size/weight sensitivity | Two buckets: large (18pt/14pt bold) or normal | Continuous — thin text needs more contrast than bold |
| Output | Ratio (1:1 .. 21:1) | Lc (Lightness contrast) score, -108 .. +106 |
| Body text minimum | 4.5:1 (normal), 3:1 (large) | Lc 75 (large/bold) .. Lc 90 (small/regular) |
| Large text / headlines | 3:1 | Lc 60-75 |
| Non-text (icons, UI borders, focus rings) | 3:1 (via 1.4.11) | Lc 45-60 |
| Decorative | n/a | Lc 30 |
| Invisible threshold | — | Lc <15 never for functional |
| Tools | WebAIM contrast checker, Stark, axe | apca-w3, apcach, Harmonizer, OKLCH.net |

### When to use which

| Scenario | Use |
|---|---|
| Legal/compliance pass today (EAA, ADA, Section 508) | WCAG 2.x — required by regulation |
| Designing a new palette for maximum readability | APCA — perceptually accurate |
| Audit of dark mode where WCAG 2.x gives false positives on dark text | APCA for design review, WCAG 2.x for compliance claim |
| Icon / UI border contrast | APCA Lc 45+ AND WCAG 2.x 3:1 (belt and suspenders until WCAG 3 ships) |

Palette construction, OKLCH lightness ramps, and how to build a token set that passes both methods: `references/design/01-color-oklch.md`. The WCAG 2.x math itself is section 5 above.

## 7. Color contrast in real UI — the traps

### Trap 1: button on tinted background

Button sits on a card that has its own tint. Contrast must pass against the CARD color, not the page background.

```css
/* page bg: oklch(98% 0 0), near white */
.card { background: oklch(94% 0.02 250); } /* subtle tint */
.card .button {
  background: oklch(55% 0.2 250);          /* brand */
  color: white;
  /* verify: button bg vs CARD bg >= 3:1 (non-text contrast, 1.4.11) */
  /* verify: button text vs button bg >= 4.5:1 (1.4.3) */
}
```

### Trap 2: focus ring contrast — TWO comparisons

Focus ring must pass 3:1 against BOTH:
- the focused element (so you can see the ring against the element)
- the surrounding background (so the ring is visible when it extends past the element)

```css
:focus-visible {
  outline: 2px solid var(--ring);         /* --ring must pass 3:1 vs element AND page */
  outline-offset: 2px;                     /* offset reveals page bg between element and ring */
}
```

A gray ring on a white button on a light-gray page fails against both. A brand-blue ring usually passes both.

### Trap 3: disabled states

Disabled controls are exempt from contrast rules, BUT if disabled-vs-enabled is only signaled by contrast, users can't tell state. Add `aria-disabled` AND visible icon/label change.

### Trap 4: placeholder text

Placeholder text is NOT exempt. Chrome's default placeholder gray (`#757575` on white) is borderline. If placeholder doubles as help text, it must meet 4.5:1 — prefer a separate `<small>` hint.

## 8. ARIA roles, states, properties — minimal table per pattern

Use W3C WAI-ARIA Authoring Practices (APG — https://www.w3.org/WAI/ARIA/apg/) for full state machines and keyboard maps. This is the pocket reference.

| Pattern | Role | Required states/props | Keyboard |
|---|---|---|---|
| Button | native `<button>` | `aria-pressed` if toggle; `aria-expanded` if disclosure; `aria-disabled` or `disabled` | Enter, Space |
| Link | native `<a href>` | `aria-current="page"` if nav | Enter |
| Dialog (modal) | `role="dialog"` `aria-modal="true"` | `aria-labelledby` (title) or `aria-label`; `aria-describedby` (body) | Esc closes; Tab traps inside |
| Alertdialog | `role="alertdialog"` | Same as dialog + must be urgent | Esc closes |
| Tabs | `role="tablist"` on container; `role="tab"` on triggers; `role="tabpanel"` on panels | `aria-selected` on active tab; `aria-controls` on tab -> panel id; `aria-labelledby` on panel -> tab id | Left/Right to move; Home/End; optional Tab moves out |
| Listbox | `role="listbox"` on container; `role="option"` on items | `aria-selected` on active option; `aria-multiselectable` if multi | Up/Down, Home/End, type-ahead |
| Combobox | `role="combobox"` on input | `aria-expanded`, `aria-controls` (listbox id), `aria-activedescendant` (focused option id) | Up/Down, Enter, Esc |
| Slider | `role="slider"` | `aria-valuemin`, `aria-valuemax`, `aria-valuenow`, `aria-valuetext` (human-readable) | Left/Right, Home/End, PageUp/Down |
| Tree | `role="tree"`, `role="treeitem"`, `role="group"` | `aria-expanded` on expandable nodes; `aria-selected` | Arrows to navigate, Right to expand, Left to collapse |
| Grid | `role="grid"`, `role="row"`, `role="gridcell"` | `aria-rowindex`, `aria-colindex` if virtualized | Arrows, Home/End, PageUp/Down, Ctrl+Home/End |
| Menu (app menu, not nav) | `role="menu"`, `role="menuitem"` | `aria-haspopup`, `aria-expanded` on trigger | Arrows, Enter, Esc, type-ahead |
| Disclosure | native `<button>` + `<div>` | `aria-expanded` on button; `aria-controls` -> panel id | Enter, Space |
| Tooltip | `role="tooltip"` | `aria-describedby` on trigger -> tooltip id | Esc dismisses; not focusable itself |
| Progressbar | `role="progressbar"` | `aria-valuenow`, `aria-valuemin`, `aria-valuemax`, or `aria-valuetext` for "indeterminate" | n/a |
| Switch | `role="switch"` | `aria-checked` (true/false, not mixed) | Enter, Space |
| Checkbox (tri-state) | `role="checkbox"` | `aria-checked="mixed"` for indeterminate | Space |
| Breadcrumb | `nav[aria-label="Breadcrumb"]` + `<ol>` | `aria-current="page"` on last item | Tab |
| Data table (static) | native `<table>` | `<caption>` names it; `<th scope="col">` on column headers; `<th scope="row">` on row headers; `headers`/`id` when headers span or a cell has more than one governing header; `aria-sort` on the one sorted header | Tab through interactive cells only; a static table is not a widget |

### Data table semantics

`<td>` cells carry no header association. Without `scope`, a screen reader announces "1,240" instead of "EU, March, 1,240", which is why "Data tables have headers" is HIGH in section 11.

```html
<table>
  <caption>Revenue by region, Q1 2026 (USD thousands)</caption>
  <thead>
    <tr>
      <th scope="col">Region</th>
      <th scope="col">
        <button type="button">March</button>
      </th>
    </tr>
  </thead>
  <tbody>
    <tr><th scope="row">EU</th><td>1,240</td></tr>
  </tbody>
</table>
```

Minimum bar: a `<caption>` (visually hidden is fine), `scope` on every `<th>`, `<th scope="row">` for the identifying cell of each row, `headers`/`id` for irregular tables, `aria-sort` on exactly one header when sorting is available, and a `role="status"` announcement after a sort re-orders the rows. A `<div>` grid pretending to be a table needs the full `table`/`rowgroup`/`row`/`columnheader`/`cell` role set plus `aria-rowindex`/`aria-colindex` when virtualized. Worked examples, the div-grid pattern, and the table anti-pattern list: `references/accessibility/04-screen-reader.md` section 10.

## 9. Form accessibility

### Required patterns

```html
<!-- Explicit label — NOT placeholder-as-label -->
<label for="email">Email</label>
<input id="email" type="email" name="email"
       autocomplete="email"
       required aria-required="true"
       aria-describedby="email-help email-error"
       aria-invalid="false" />
<small id="email-help">We'll never share your email.</small>
<p id="email-error" hidden>Enter a valid email address.</p>

<!-- On invalid state -->
<input ... aria-invalid="true" aria-errormessage="email-error" />
<p id="email-error">Enter a valid email address.</p>

<!-- Grouped fields (radio, related checkboxes) -->
<fieldset>
  <legend>Shipping method</legend>
  <label><input type="radio" name="ship" value="std"> Standard</label>
  <label><input type="radio" name="ship" value="exp"> Express</label>
</fieldset>
```

### Rules

| Rule | Why |
|---|---|
| Every input has a programmatic label | `<label for>` preferred; `aria-label` fallback; `aria-labelledby` for complex cases |
| Placeholder is NEVER a label | Disappears on focus, low contrast by default, screen readers inconsistent |
| `autocomplete` attr on known-purpose fields | 1.3.5 Identify Input Purpose + password managers |
| `aria-required` mirrors `required` | Some screen readers only read aria version |
| `aria-invalid="true"` on invalid fields | Announces state to screen readers |
| `aria-errormessage` points to error id | Associates error text with field (improved support in 2025) |
| Error summary above form on submit | Second chance to announce; link to each error field |
| Errors appear INLINE with the field | Not just in a summary |
| `inputmode` on mobile inputs | Right keyboard (numeric, email, url) |
| Group related controls with `<fieldset><legend>` | Radio groups, address blocks |
| Don't use color alone for error state | Red border + error icon + error text |

## 10. Anti-patterns flagged as CRITICAL

| Anti-pattern | Why it's critical | Fix |
|---|---|---|
| Custom button (`<div onclick>`) without `role="button"` AND `tabindex="0"` AND Enter/Space handlers | Not focusable, not announced as button, not keyboard-operable | Use `<button>`. If you can't, add role + tabindex + handlers + `aria-pressed` if toggle |
| Modal/dialog without focus trap | Tab escapes dialog into hidden page, breaking context | Use Radix Dialog / react-aria / focus-trap library, or implement first/last focusable cycling |
| Color as the only signal (red text for errors, green for success) | Color-blind users and low-vision users miss state | Add icon + text label ("Error:", "Success:") |
| Form fields without programmatic labels | Screen reader announces "edit text" with no context | `<label for>` required |
| Click-only drag-and-drop with no keyboard alternative | Fails 2.1.1 Keyboard AND 2.5.7 Dragging (AA) | Add up/down buttons (2.5.7) AND arrow-key handling with a live-region announcement (2.1.1); do not use the deprecated `aria-grabbed` |
| Auth requiring typed captcha or memorized-only password | Fails 3.3.8 | Allow paste + password manager; offer WebAuthn/magic link |
| Target sizes <24x24 with no spacing buffer | Fails 2.5.8 | 24x24 min (44x44 preferred); or satisfy the spacing exception per the two-case rule in section 2: between two undersized targets `gap >= 24 - (size_a + size_b) / 2` (two 16x16 need 8px); against any neighbour of 24px or more `gap >= (24 - size) / 2` (a 16x16 beside a 44x44 needs 4px). Never quote one flat number |
| Sticky header that fully hides focused input | Fails 2.4.11 | `scroll-margin-top` on focusables; or `scroll-padding-top` on `<html>` |
| `outline: none` with no `:focus-visible` replacement | Fails 2.4.7 | Always provide a visible focus indicator |
| Autoplaying video >5s with no pause | Fails 2.2.2 | Pause/stop control, always. Additionally do not autoplay under `prefers-reduced-motion: reduce` (platform expectation, not a substitute for the control) |
| Any time limit (session, OTP, quiz) with no turn-off / adjust / extend | Fails 2.2.1 | Turn off, adjust to >= 10x the default, or warn >= 20s before expiry and allow >= 10 extensions; exempt only if real-time, essential, or > 20 hours |
| Tooltip that disappears when mouse leaves trigger (but cursor is over tooltip) | Fails 1.4.13 | Tooltip must be hoverable and dismissible via Esc |

## 11. Severity mapping for accessibility findings

When a review or audit flags an accessibility gap, use this table to assign finding severity by check category (not by individual SC — see section 4 for the SC-level checklist). This is the severity vocabulary reviewers should use when writing up WCAG failures as findings.

### Semantics and labeling

| Check | Standard | Severity if failed |
|---|---|---|
| All interactive elements have accessible names | WCAG 4.1.2 | CRITICAL |
| Form inputs have associated labels | WCAG 1.3.1 | CRITICAL |
| Images have alt text (decorative = `alt=""`) | WCAG 1.1.1 | CRITICAL (functional) / LOW (decorative) |
| Landmarks/regions used for page structure | WCAG 1.3.1 | MEDIUM |
| Headings follow logical hierarchy | WCAG 1.3.1 | MEDIUM |
| Data tables have headers (`<caption>`, `<th scope>`, `headers`/`id` for irregular tables, `aria-sort` on sortable columns) | WCAG 1.3.1 | HIGH |
| Language declared | WCAG 3.1.1 | MEDIUM |
| Status changes announced to assistive tech | WCAG 4.1.3 | HIGH |

### Keyboard and focus

| Check | Standard | Severity if failed |
|---|---|---|
| All functionality reachable by keyboard | WCAG 2.1.1 | CRITICAL |
| No keyboard traps | WCAG 2.1.2 | CRITICAL |
| Focus order matches visual order | WCAG 2.4.3 | HIGH |
| Focus visible on all interactive elements | WCAG 2.4.7 | CRITICAL |
| Focus not obscured by sticky/fixed elements | WCAG 2.4.11 | HIGH |
| Skip navigation link available | WCAG 2.4.1 | MEDIUM |
| Custom widgets support expected keyboard patterns | WCAG 2.1.1 | HIGH |
| Escape closes modals/overlays | WCAG 2.1.1 | HIGH |
| Focus returns to trigger after overlay closes | Best practice | MEDIUM |

### Visual accessibility

| Check | Standard | Severity if failed |
|---|---|---|
| Text contrast >= 4.5:1 (normal) / 3:1 (large) | WCAG 1.4.3 | CRITICAL |
| Non-text contrast >= 3:1 | WCAG 1.4.11 | HIGH |
| Not relying on color alone for meaning | WCAG 1.4.1 | HIGH |
| Text resizable to 200% without loss | WCAG 1.4.4 | HIGH |
| Content reflows at 320px (no horizontal scroll) | WCAG 1.4.10 | HIGH |
| Spacing adjustable without loss of content | WCAG 1.4.12 | MEDIUM |

### Motor accessibility

| Check | Standard | Severity if failed |
|---|---|---|
| Touch targets >= platform minimum (see section 12 comparison table) | WCAG 2.5.8 | HIGH; CRITICAL when the undersized target is on the primary task path |
| No drag-only actions without alternative | WCAG 2.5.7 | HIGH |
| No multi-pointer required gestures without alternative | WCAG 2.5.1 | HIGH |
| Spacing between targets that already meet 24x24 (no accidental activation) | Best practice, not 2.5.8 (an undersized target with insufficient spacing is the 2.5.8 failure above) | MEDIUM |

### Motion accessibility

| Check | Standard | Severity if failed |
|---|---|---|
| `prefers-reduced-motion` respected | 2.2.2 Pause, Stop, Hide (A) and 2.3.1 Three Flashes (A) for auto-running motion; 2.3.3 Animation from Interactions (**AAA**) for interaction-triggered motion | CRITICAL |
| No content flashes > 3/second | WCAG 2.3.1 | CRITICAL |
| Auto-playing content can be paused/stopped | WCAG 2.2.2 | HIGH |
| Motion not required for any functionality | WCAG 2.5.4 | HIGH |

Note on level: `prefers-reduced-motion` is a platform expectation above the AA floor, not itself an AA criterion. Severity is written from user impact; the citation must state the level honestly. Full citation-picking table: `references/accessibility/03-motion-reduce.md` section 1.

### Understandable: forms, errors, and flow

This is the block that catches the defects users describe as "the app is confusing" rather than "the app is broken": a checkout that re-asks for the email you typed two steps ago, an error that says "invalid" and nothing else, a session that expires mid-form, a Help link that moves between pages. None of these produce an axe violation, and all of them are conformance failures.

| Check | Standard | Severity if failed |
|---|---|---|
| Every error states WHICH field failed, in text (not color or icon alone) | WCAG 3.3.1 Error Identification (A) | HIGH |
| Every error suggests a correction when one is knowable ("Use the format 12/2028", not "Invalid date") | WCAG 3.3.3 Error Suggestion (AA) | HIGH |
| Labels and format instructions are present BEFORE input, not revealed only on failure | WCAG 3.3.2 Labels or Instructions (A) | HIGH |
| Legal, financial, or data-modifying submissions are reversible, checked, or confirmable | WCAG 3.3.4 Error Prevention (AA) | HIGH |
| A multi-step flow never re-asks for information already given in the same process | WCAG 3.3.7 Redundant Entry (A) | HIGH |
| Authentication allows paste, password managers, and passkeys; no memorization or transcription test without an alternative | WCAG 3.3.8 Accessible Authentication (AA) | HIGH |
| Help (contact link, chat, FAQ) sits in the same relative position on every page that has it | WCAG 3.2.6 Consistent Help (A) | MEDIUM |
| Focusing a control does not change context (no auto-submit, no new window, no navigation on focus) | WCAG 3.2.1 On Focus (A) | HIGH |
| Changing a value does not change context without warning (no auto-submit on select, no reload on toggle) | WCAG 3.2.2 On Input (A) | HIGH |
| Navigation appears in the same relative order across pages | WCAG 3.2.3 Consistent Navigation (AA) | MEDIUM |
| The same function carries the same label and icon everywhere | WCAG 3.2.4 Consistent Identification (AA) | MEDIUM |
| Page language is declared, and foreign-language passages are marked | WCAG 3.1.1 (A) / 3.1.2 (AA) | MEDIUM |

### Timing and interruptions

| Check | Standard | Severity if failed |
|---|---|---|
| Any time limit can be turned off, adjusted, or extended (warn at least 20s before expiry; allow at least 10 extensions or 10x adjustment) | WCAG 2.2.1 Timing Adjustable (A) | HIGH |
| Session expiry does not silently discard entered data | WCAG 2.2.1 (A), 2.2.5 (AAA) for re-auth without data loss | HIGH |
| Moving, blinking, or auto-updating content running longer than 5s can be paused, stopped, or hidden | WCAG 2.2.2 Pause, Stop, Hide (A) | HIGH |
| Auto-advancing carousels and auto-refreshing feeds have a visible pause control | WCAG 2.2.2 (A) | HIGH |
| Single-character keyboard shortcuts can be disabled, remapped, or require a modifier | WCAG 2.1.4 Character Key Shortcuts (A) | MEDIUM |

### Media

| Check | Standard | Severity if failed |
|---|---|---|
| Prerecorded video with audio has captions | WCAG 1.2.2 Captions (Prerecorded) (A) | HIGH |
| Prerecorded audio-only has a transcript; video-only has a transcript or audio description | WCAG 1.2.1 (A) | HIGH |
| Prerecorded video has audio description or a full text alternative | WCAG 1.2.3 (A) / 1.2.5 (AA) | MEDIUM; HIGH when the video carries information available nowhere else |
| Live audio in synchronized media has captions | WCAG 1.2.4 Captions (Live) (AA) | HIGH |
| Audio that autoplays for more than 3s can be paused or muted independently of system volume | WCAG 1.4.2 Audio Control (A) | HIGH |
| Captions are real captions, not burned-in open captions that break at 200% zoom | WCAG 1.2.2 (A) plus 1.4.4 | MEDIUM |

### Dynamic content

| Check | Failure mode | Severity |
|---|---|---|
| Live regions announce updates | `aria-live="polite"` for non-urgent, `"assertive"` for critical | HIGH |
| Loading states communicated | `role="status"` or `role="alert"` | HIGH |
| Error messages associated with inputs | `aria-describedby` + `aria-invalid` | HIGH |
| Toast/snackbar messages accessible | Announced via live region with sufficient display time | MEDIUM |

### Confidence rules for accessibility findings

- Automation finds violation + artifact supports it: **strong finding**.
- Automation clean but screenshots/trace suggest an issue: **"needs manual verification"**.
- Input lacks semantics or accessibility-tree evidence: **soften claims, don't guess**.
- Never claim "accessible" based solely on a clean automation scan — axe/Lighthouse-class tools catch roughly 30-40% of issues; manual screen-reader testing is required for the rest.

## 12. Touch target size — platform comparison

WCAG 2.2's 24px minimum (section 2, criterion 2.5.8) is the compliance floor, not the design target. When reviewing UI meant to ship on or alongside native platforms, check against the stricter platform HIG too — Apple and Material both require larger minimums than WCAG's floor.

| Standard | Minimum | Recommended |
|---|---|---|
| Apple HIG | 44x44pt | 44x44pt |
| Material Design 3 | 48x48dp | 48x48dp |
| WCAG 2.2 (2.5.8) | 24x24 CSS px | 44x44 CSS px |

Practical rule: design to 44x44 (or 48x48 on Android) as the default touch target size. Treat WCAG's 24px as the legal floor for web-only surfaces that will never ship as a native or cross-platform app shell — anything with an Apple or Android target should hold the line at 44/48.

## 14. Additional accessibility media queries

Beyond `prefers-reduced-motion` (covered in `references/accessibility/03-motion-reduce.md`), three further user-preference and platform media queries carry accessibility weight. Check and honor each where it applies; missing them is a common gap even in otherwise accessible UI.

| Query | What it signals | One-line guidance |
|---|---|---|
| `@media (prefers-contrast: more)` | User wants higher contrast | Push text and border contrast toward AAA (7:1 text, stronger UI-element borders); strengthen tokens rather than adding new colors |
| `@media (prefers-contrast: less)` | User finds high contrast harsh (some low-vision, migraine, and light-sensitivity users) | Soften pure-black-on-white and harsh edges, but never drop below the AA floor (4.5:1 text) |
| `@media (forced-colors: active)` | Windows High Contrast Mode is on; the OS replaces author colors | Don't fight it -- use system color keywords, keep `border`/`outline` on interactive and bounding elements (they survive forced colors where `background-color`/`box-shadow` do not), verify focus rings remain visible, and reach for `forced-color-adjust` only when essential |
| `@media (prefers-reduced-transparency: reduce)` | User wants fewer translucent / blurred surfaces | Replace `backdrop-filter` glassmorphism and low-opacity overlays with solid backgrounds; this also recovers the contrast and legibility those effects erode |

```css
@media (prefers-contrast: more)    { /* increase contrast */ }
@media (prefers-contrast: less)    { /* reduce harsh contrasts */ }
@media (forced-colors: active)     { /* Windows High Contrast */ }
@media (prefers-reduced-transparency: reduce) { /* solid backgrounds */ }
```

`forced-colors: active` is the most commonly missed of the four: in Windows High Contrast Mode the browser strips author `background-color` and `box-shadow`, so any component that conveyed state or boundaries only through those becomes invisible. Verify that borders and focus indicators survive.
